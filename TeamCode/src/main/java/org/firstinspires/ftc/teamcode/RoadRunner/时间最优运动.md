# 自动轨迹「时间最优」运动指南

本文件说明如何让**所有移动类 Action**（`Auto/AutoActions/` 下的 `GoTo*` 系列）
在给定约束下以**最短时间**走完整条路径，并给出后续的标定 / 验证 / 维护操作方法。

> 「时间最优」的定义（本项目的验收标准）：
> **起步以最大加速度冲到最大速度 → 中段一直保持最大速度巡航 → 末端以最大减速度、
> 最短时间停止。** 整条路径（含所有途经点）满足该性质。
> 在给定「最大速度 + 最大加速度」下，这就是数学上的最短耗时运动
> （bang-bang 控制 / 梯形速度曲线）。

---

## 1. 原理

Road Runner 1.0.1 的 `TrajectoryBuilder` 会**自动**求解时间最优 profile：
在给定的速度约束 `VelConstraint` 与加速度约束 `AccelConstraint` 之内，用最简单的
「全油门加速 → 巡航 → 全力刹车」把位移做完。这是可直接解析验证的：

设最大速度 `v`、最大加速度（与最大减速度绝对值）`a`、位移 `d`，则最短耗时

| 情况 | 条件 | 最短耗时 t |
|------|------|-----------|
| **梯形**（能冲到 v） | `d ≥ v²/a` | `v/a + (d − v²/a)/v + v/a` |
| **三角形**（冲不到 v） | `d < v²/a` | `2·√(d/a)` |

`d ≥ v²/a` 时：前 `v/a` 秒全加速（走 `v²/(2a)`）、中段以 `v` 巡航
（走 `d − v²/a`）、末 `v/a` 秒全力减速（再走 `v²/(2a)`）——即梯形曲线。

**途经点连续性**：在**同一个** `TrajectoryActionBuilder` 内链式调用
`strafeToLinearHeading(...)` 得到的途经点，段间**速度连续、不中途停车**
（不是"到点刹车再重新起步"）。可用等效替换验证：`A→B→C` 共线链式的总时长
与 `A→C` 单段**完全相等**（见第 5 节 `TrajectoryProfileTest`）。

## 2. 代码中的实现位置

约束的**唯一来源**是 [`MecanumDrive.Params`](file:///d:/Github/BIOBUZZ/TeamCode/src/main/java/org/firstinspires/ftc/teamcode/RoadRunner/MecanumDrive.java#L71-L113) 的五个参数，
在 drive 构造时被固化成三个 `final` 默认约束，再由
[`actionBuilder(Pose2d)`](file:///d:/Github/BIOBUZZ/TeamCode/src/main/java/org/firstinspires/ftc/teamcode/RoadRunner/MecanumDrive.java#L832-L846) 传给每一个轨迹：

```
Params 五个参数
  ├─ maxWheelVel ─┐
  │               ├─► defaultVelConstraint   = MinVelConstraint( WheelVelConstraint(maxWheelVel), AngularVelConstraint(maxAngVel) )
  ├─ maxAngVel ───┘
  ├─ maxAngVel ─┐
  │             ├─► defaultTurnConstraints   = TurnConstraints(maxAngVel, −maxAngAccel, +maxAngAccel)
  ├─ maxAngAccel┘
  ├─ minProfileAccel ─┐
  │                   ├─► defaultAccelConstraint = ProfileAccelConstraint(minProfileAccel, maxProfileAccel)
  └─ maxProfileAccel ─┘
                                  ▼
                        actionBuilder(beginPose) → TrajectoryActionBuilder
                                  ▼
        所有 Action：drive.actionBuilder(...).strafeToLinearHeading(...) 链 .build()
```

| 参数 | 单位 | 作用 | 当前值（模板起点） |
|------|------|------|--------------------|
| `maxWheelVel` | in/s | **巡航最大速度**（轮速约束，经运动学映射到底盘平移速度） | 50 |
| `minProfileAccel` | in/s² | **减速度上限**（负值；其绝对值 = 最大刹车能力） | −50 |
| `maxProfileAccel` | in/s² | **加速度上限**（加速能力） | 50 |
| `maxAngVel` | rad/s | 转向最大角速度 | π |
| `maxAngAccel` | rad/s² | 转向最大角加速度 | π |

**关于减速对称性**：要做到「以最短时间、最快速度停止」，`|minProfileAccel|` 应**不小于**
`maxProfileAccel`（默认已取对称 `−50 / +50`）。若实测刹车能力**强于**起步（例如刹车时
抓地更好），可以把它调到比 `−maxProfileAccel` **更大（更负）**，进一步缩短刹车段。
Road Runner 官方模板默认为 `−30 / +50`（不对称），那会让减速慢于加速，**不满足**本项目要求，
已在本仓库改为对称。

**注意：约束在 drive 构造时固化。** `defaultTurnConstraints` / `defaultVelConstraint` /
`defaultAccelConstraint` 都是 `final` 字段，运行时在 Dashboard 里改 `Params` 的值
**不会**改变已构造好的 drive 的约束。修改后必须**重启 OpMode**（重建 drive）才生效。

## 3. 编写要求（对所有 Action 生效）

要让「时间最优」成立，写 Action 时必须遵守：

1. **一段移动只用一个 `actionBuilder` 链**。
   把路径拆成多个 `actionBuilder`（例如先 build 一段、跑完再 build 下一段）
   = 多段独立轨迹，段与段之间**必然停车**，直接破坏时间最优。
   需要中途经过的中间点，一律作为**链式途经点**写进同一个 builder。
2. **只有确实要求「停稳」时才单独 build 一条轨迹**（例如终点就是位姿，不需要中间点）。
3. **不要为了"稳"而调低约束**：调低 `maxWheelVel` / `|minProfileAccel|` / `maxAngVel`
   / `maxAngAccel` 都会**直接变慢**。约束应取到「打滑 / 跟踪发散之前的物理极限」。
4. 轨迹在**构造时刻**固化，因此应在**入队前、机器人位置基本确定后**再 `new` 该 Action。

当前仓库内的移动类 Action 已逐一核对，**均只用一个 `actionBuilder` 链**：

| Action | 轨迹构建 |
|--------|---------|
| `GoToStopPose` | 单 builder，单段 |
| `GoToShootAreaAction` | 单 builder，单段 |
| `GoToEatPointAction` | 单 builder，单段 |
| `GoToNearestEatPointAction` | 单 builder，单段 |
| `GoToShootAreaNearestVerticesAction` | 单 builder，**两个链式途经点**（不中途停车） |
| `HiveRouteAction` 及其 4 个子类 | 单 builder，**多个链式途经点**（不中途停车） |
| `AutoAimAction` | **例外**：原地 PD 转向，非轨迹类，**不是**时间最优 |
| `EatAction` | **例外**：不移动，仅运转集球器 |

## 4. 操作方法：标定「规划最优 = 实际最快」

Road Runner 给出的是**理论上**的最短时间；机器人实际能否做到，取决于五个参数是否
等于「硬件真实极限」。标定流程如下。

### 4.1 前置

- 确认 `MecanumDrive.PARAMS` 中 `inPerTick` / `lateralInPerTick` / `trackWidthTicks`
  以及 `kS` / `kV` / `kA` 已经标定正确（否则轨迹跟随本身就不到位）。
- 安全：把机器人放到空旷处，或架起驱动轮；准备好随时急停（按驱动站 STOP）。

### 4.2 标定 OpMode（Driver Station 组名 `quickstart`）

由 [`TuningOpModes`](file:///d:/Github/BIOBUZZ/TeamCode/src/main/java/org/firstinspires/ftc/teamcode/RoadRunner/tuning/TuningOpModes.java#L290-L306) 注册，用到的是：

| OpMode | 用途 |
|--------|------|
| `ForwardRampLogger` / `LateralRampLogger` | 记录向前 / 横向的「指令 → 实测速度」斜坡，**读最大速度** |
| `AngularRampLogger` | 记录转向斜坡，**读最大角速度** |
| `ForwardPushTest` / `LateralPushTest` | 推车测 `kS`（静摩擦） |
| `ManualFeedforwardTuner` | 调 `kV` / `kA` |
| `MecanumMotorDirectionDebugger` | 核对四轮转向 / 方向 |
| `SplineTest` / `LocalizationTest` | 综合验证轨迹跟随与定位 |

> 本仓库**没有** Road Runner 1.0 以外的「MaxVelocity / MaxAcceleration」专用自动标定 OpMode；
> 最大速度由 ramp logger 的**饱和值**读出，最大加速度则由 `maxProfileAccel` 直接给定并按
> 4.4 的实机判据迭代。

### 4.3 填参数

1. 打开 FTC Dashboard → **Config → `MecanumDrive`** 分组，修改五个参数。
2. 目标初值：
   - `maxWheelVel` ← ramp logger 实测的最大平移速度的 **80%~90%**（留跟踪余量）；
   - `maxProfileAccel` ← 起步不空转的最大加速度；`minProfileAccel = −maxProfileAccel`；
   - `maxAngVel` ← 角速度 ramp 实测饱和值的 80%~90%；
   - `maxAngAccel` ← 起步不空转的最大角加速度。
3. **重启 OpMode**，让新的约束生效（见第 2 节）。

### 4.4 实机判据（迭代）

对每个移动类 Action 跑一遍对应的 `Test:` OpMode（组名 **ActionTest**，见
[`Actions.md`](file:///d:/Github/BIOBUZZ/TeamCode/src/main/java/org/firstinspires/ftc/teamcode/Auto/AutoActions/Actions.md)），观察：

| 现象 | 判断 | 处理 |
|------|------|------|
| 速度曲线有**平台段**、末端在终点附近停稳、无过冲 | 达标 | 可尝试再加大约束 |
| 中段达不到 `maxWheelVel`（打滑空转） | 约束超过抓地极限 | 减小 `maxWheelVel` / `maxProfileAccel` |
| 末端**冲过**目标再回拉 | 减速度超过刹车抓地 | 减小 `|minProfileAccel|` |
| 转向长期欠调 / 抖动 | 角加速度过大 | 减小 `maxAngAccel` ，必要时减 `maxAngVel` |
| 走 Hive 路线时外接矩形越界 / 擦到禁线 | 过冲吃掉了避让余量 | 减小约束，或加大 `HypParams.hiveAvoidClearanceIn` |

**原则**：每轮只动一个参数，逐步逼近「打滑 / 跟踪发散临界点」，
最终取**略保守**的值（临界值 × 0.8~0.9），因为比赛时电量、地面、载重都会变。

## 5. 验证方法

### 5.1 JVM 单元测试（离线、可回归）

[`TrajectoryProfileTest`](file:///d:/Github/BIOBUZZ/TeamCode/src/test/java/org/firstinspires/ftc/teamcode/RoadRunner/TrajectoryProfileTest.java) 守护两条性质：

- `chainedCollinearSegmentsDoNotStopAtWaypoints`：`A→B→C` 链式两段与 `A→C` 单段
  的**总时长完全相等** → 证明途经点间速度连续、不中途停车。
- `longMoveHasTrapezoidalProfile`：起点/终点速度≈0、峰值达到 `maxWheelVel`、
  **总时长等于第 1 节的解析最短耗时**、且存在高速巡航段（梯形而非三角形）。

运行：

```bash
.\gradlew.bat :TeamCode:testDebugUnitTest --tests "org.firstinspires.ftc.teamcode.RoadRunner.TrajectoryProfileTest"
```

> 任何 Action 若把一段移动拆成多个 `actionBuilder`，都会破坏上述性质；
> 这是防止"时间最优"被后续改坏的**回归护栏**。

### 5.2 实机验证

- 用 `Test:` OpMode 跑目标 Action，Dashboard 上查看**目标速度 / 实际速度**曲线，
  确认有平台段且末端收敛。
- 用 `SplineTest` 验证整体轨迹跟随质量。

## 6. 注意事项与已知边界

- **「规划最优」≠「实际最快」**：打滑、跟踪误差、定位误差、电压跌落都会拖慢实际耗时。
  标定就是把两者拉近；拉近的极限是抓地力。
- `HypParams.maxV` / `HypParams.maxOmega` 只作用于**手动底盘**（`Chassis`），
  与**自动轨迹无关**，不要混淆。
- `AutoAimAction` 是 PD 渐近收敛的原地转向，**不是**时间最优；它只负责最后的精确瞄准，
  不参与本文件的达标范围。
- Hive 路线类 Action 的避让间隙 `HypParams.hiveAvoidClearanceIn` 是**实机标定项**；
  约束拉满后过冲变大，可能需要同步加大该余量（见 4.4 表末行）。
- 单位约定：长度 **英寸**、速度 **英寸/秒**、角度 **弧度**、角速度 **弧度/秒**。
